# Dashboard

`render_dashboard` composes the other Sigil widgets into **one tiled grid** — a
KPI row above a couple of charts, a map beside a table, whatever the question
needs. It is the only widget whose payload embeds other widgets' payloads.

Live examples are under **Widgets → Dashboard**; this page explains the
composition model behind them.

## Composition model

A dashboard is an ordered list of `tiles`. Each tile names a widget `type` and
carries that widget's **own payload** verbatim — exactly the object its
`render_<type>` tool would take:

```ts
render_dashboard({
  title: "Regional overview",
  columns: 2,
  tiles: [
    { type: "stat-panel", payload: { /* a render_stat_panel payload */ }, colSpan: 2 },
    { type: "map",        payload: { /* a render_map payload        */ }, colSpan: 2 },
    { type: "bar-chart",  payload: { /* a render_bar_chart payload  */ } },
    { type: "pie-chart",  payload: { /* a render_pie_chart payload  */ } },
  ],
})
```

So there is no new data language to learn: if you can describe a widget on its
own, you can drop it into a dashboard by pairing its `type` with its payload.

## Tile types

Any widget can be a tile **except the dashboard itself** (no dashboard-in-dashboard):
`bar-chart`, `line-chart`, `pie-chart`, `table`, `scatter-chart`, `treemap`,
`heatmap`, `stat-panel`, `sankey`, and `map`.

Internally the tile `type` is looked up in a small type→`{ View, isPayload }` map
(`src/widgets/shared/widget-views.ts`). That module imports each widget's
presentational `*View` and its `guard.ts` — never its `App.tsx` entry, which would
call `mountWidget` on import — so composing widgets stays free of MCP-mount side
effects. Making a widget tileable means adding it to that map **and** to the
`render_dashboard` tool's tile-type enum, which is what the model picks from.

## When a tile is broken

A tile's `payload` bypasses the tool schema entirely — `render_dashboard` types it
as an opaque object, because it is another widget's payload — so the dashboard
validates each tile itself and contains the damage to one card:

| Situation | What renders |
|---|---|
| No widget of that `type` | **Unknown widget** — naming the type it was given |
| `type` is `dashboard` | **Nested dashboard** — the widget exists, it just cannot nest |
| Payload fails that widget's guard | **Invalid `<type>` tile** |
| The view throws while rendering | **Could not render `<type>`** — from a per-tile error boundary |

In every case the sibling tiles render normally. The **Degraded** story shows the
first three side by side; the fourth has no preset, because provoking it needs a
payload that satisfies its widget's guard and still throws.

## Layout

- **`columns`** — grid width, 1–4 (default `2`).
- **`colSpan`** (per tile) — how many columns the tile spans, `1..columns`
  (default `1`). A `colSpan` equal to `columns` gives a full-width band, which
  is how a stat-panel header row or a wide map is placed.

Tiles lay out left-to-right, top-to-bottom in payload order. Each tile keeps its
own title and toolbar (Copy CSV / PNG), so it behaves exactly like the
standalone widget — just inside a card.

## When to use

Reach for a dashboard when several related views belong together in one glance —
a metrics overview, a report header, a geo + breakdown pairing. For a single
view, call that widget's own `render_*` tool directly.
